## 二、问题背景（为什么必须重写）

| 项 | 事实 |
|---|---|
| 原方案 | 千千静听官方歌词插件 `AddIn\ttp_lrcsh.dll` + NCAB.exe（本地 HTTP 歌词服务器，127.0.0.1:89） |
| Win11 故障根因 | **Smart App Control 强制模式**（`VerifiedAndReputablePolicyState=1`）以「恶意二进制信誉」拦截 **UPX 加壳的 NCAB.exe**（错误 4551「应用程序控制策略已阻止此文件」）|
| SAC 可关闭吗 | **不能**。SAC 一旦开启只能重装系统关闭 —— 所以原版方案在原机上永久不可用，必须替换实现 |
| 对 SAC 的实测结论 | ① 全新编译的**未签名** DLL/EXE → 放行（首次加载可能有短暂异步裁定，重试即过）② **改动过带签名 DLL**（哪怕只是剥签名或改一个字节）→ 视为篡改，**被持久拦截** ③ UPX 加壳无签名 → 按恶意信誉拦截 |
| 因此的架构定案 | **不碰原版 DLL，用一个全新的未签名 DLL 整体替换它**，在进程内直接实现插件 ABI + 直连音源 API |

## 四、架构与数据流

```
TTPlayer.exe
├─ 启动时 FindFirstFileW("AddIn\ttp_*.dll") 枚举插件
├─ LoadLibrary → GetProcAddress("ttpGetSoundAddIn") → 调用
├─ 循环 factory->GetIfaceC(n, &guid, &ppv) 直到返回负 HRESULT
│    └─ guid 与内置已知 GUID 表比对（GUID_C = 歌词插件）→ 注册为歌词源
└─ 播放/切歌时：
     lyrics->GetEngine(&engine)
     engine->Initialize(宿主接口)          ← 宿主这里给回调对象
     engine->SetSongInfo(artist, title)    ← 触发搜索
     engine->SelectResult(index)           ← 用户选了某条 → 触发下载
           ↓
     我们的工作线程：QQ/酷狗 API → LRC
           ↓
     宿主回调 cb[3]（搜索结果列表） / cb[4]（歌词正文）

无 HTTP server、无 127.0.0.1:89、无外部进程；TTPlayer 关闭即全部结束。
```

构建/部署/回滚见第七节。

## 五、插件 ABI 完整规格（**交接核心，全部经反编译 + 实测验证**）

### 5.1 调用约定

- 全部 `__stdcall`，**`this` 作为显式第一个参数**（C 风格 vtable，非 C++ thiscall）
- 反编译可见函数以 `ret N` 结尾，参数全走栈
- 对象 vtable 指针位于对象首 4 字节

### 5.2 GUID 表（原版 `.rdata` 提取 + TTPlayer.exe 内置列表比对确认）

| 名称 | GUID | 用途 |
|---|---|---|
| IUnknown | `00000000-0000-0000-C000-000000000046` | 标准 |
| GUID_A | `EEC6C534-FEBA-421E-AA5D-10AC66F98784` | 工厂对象 |
| GUID_C | `9D5AE963-7DF6-4323-B4CF-FBDA159BFF15` | **歌词接口**（TTPlayer 以此识别歌词插件）|
| GUID_E | `BF17B3E8-7E33-45E7-9342-CDD34BA55AF9` | 引擎接口 |
| GUID_HOST | `6F1F38A8-3021-4E2E-BBFB-7F616A5C3D62` | 宿主中级接口（Initialize 时 QI 用）|
| GUID_CB | `CA540428-2528-4BBC-87B0-6605F21810C9` | **歌词交付回调** |

### 5.3 导出

```c
HRESULT __stdcall ttpGetSoundAddIn(void **ppv);   // 返回工厂对象（8 字节：[vtable][refcnt]）
```

### 5.4 工厂对象 vtable（4 方法）

| idx | 方法 | 说明 |
|---|---|---|
| 0 | QueryInterface(this, riid, ppv) | 支持 IUnknown / GUID_A |
| 1 | AddRef(this) | |
| 2 | Release(this) | 归零即释放 |
| 3 | **GetIfaceC(this, int mode, GUID *guidOut, void **ppv)** | **`mode` 必须是 0..1，且每多返回一个成功就多注册一份插件** |

> ⚠️ **坑（已踩）**：原版对 `mode ∈ {0,1}` 都返回成功，导致 TTPlayer 注册**两份**相同歌词插件 → 界面出现「两个本地歌词」。我们的实现**只放行 `mode==0`，`mode>=1` 返回 `E_FAIL`** 以结束宿主枚举循环 → 界面只剩一个。

### 5.5 歌词对象 vtable（9 方法，对象 12 字节 `[vtable][mode][refcnt]`）

| idx | 语义 |
|---|---|
| 0 | QueryInterface（GUID_C / IUnknown）|
| 1 | AddRef |
| 2 | Release |
| 3 | **GetEngine(this, void **ppEngine)** ← 创建引擎对象 |
| 4 | 另一个接口的 QI（含第三个 GUID）|
| 5..8 | 配置/析构辅助（未全部使用）|

### 5.6 引擎对象 vtable（8 方法，对象 0x88 字节）

| idx | 语义 | 关键点 |
|---|---|---|
| 0 | QueryInterface（GUID_E / IUnknown）| |
| 1 | AddRef | |
| 2 | Release | |
| 3 | **Initialize(this, host, initData)** | 保存 host 指针；**QI 出回调对象**（`host->QI(GUID_CB)`）；启动工作线程 |
| 4 | **SetSongInfo(this, const wchar_t *artist, const wchar_t *title)** | 投递「搜索」命令（cmd=1）|
| 5 | **SelectResult(this, int index)** | 复制选中项并投递「下载」命令（cmd=2）|
| 6 | 取配置对象 | |
| 7 | 析构（投递 cmd=3 退出线程）| |

内部字段（原版布局，仅供理解）：`+0x4c` 临界区、`+0x68` artist、`+0x6c` title、`+0x70` 选中项、`+0x7c` 错误码、`+0x80` 错误消息、`+0x84` **宿主回调**、`+0x100` mode。

### 5.7 宿主回调接口 vtable（TTPlayer 实现，我们调用）

| idx | 签名 | 说明 |
|---|---|---|
| 0..2 | QI / AddRef / Release | |
| 3 | `HRESULT cb_results(cb, int count, wchar_t **artists, wchar_t **titles)` | 交付搜索结果列表；`count=0` 表示无结果 |
| 4 | `HRESULT cb_lyric(cb, int **charCount**, const **wchar_t** *text, const wchar_t *s1, const wchar_t *s2)` | 交付歌词正文 |

> ⚠️ **坑（2026-10-24 定位并修复，最关键的 bug）**：`cb_lyric` 的第三个参数是 **UTF-16LE 宽字符串**，第二个参数是**宽字符个数**（不是字节数）。
> 我们最初按 UTF-8 字节流 + 字节数交付，TTPlayer 把 ASCII 两两打包成汉字（`[id:` → `楛㩤`），落盘的 `.lrc` 全是乱码 → 表现为「**歌词没法下载/没有歌词**」。
> 实证方法：把落盘乱码按 UTF-16LE 反推，可**精确还原**出原始 UTF-8 字节（见第九节复现命令）。
> 原版插件之所以正常，是因为旧的 NCAB 返回的 LRC 本身就是 UTF-16LE（或含该语义）。
> 现在的实现：`MultiByteToWideChar(CP_UTF8, ...)` 转换后交付，并在缓冲区尾部多留 64 个宽字符的 0 以防御越界读。

### 5.8 宿主加载器行为（TTPlayer.exe `FUN_004cabc0`）

- 只枚举 `AddIn\ttp_*.dll`（**非递归**）
- 每个 DLL → `LoadLibrary` → `GetProcAddress("ttpGetSoundAddIn")` → 循环 `GetIfaceC(0,1,2...)`
- 返回负 HRESULT 即结束该 DLL 的枚举
- GUID 不等于已知四者之一 → **安全跳过**（不会崩溃）
- 加载异常走 `_CxxThrowException`，上层有捕获（因此插件初始化失败不会拖垮播放器）

### 8.3 判断「歌词到底交付对了没有」

让 TTPlayer 播放一首歌（会自动搜索+下载），然后看落盘文件：

```bash
f=$(ls -t /d/TTPlayer/Lyrics/*.lrc | head -1); echo "$f"; head -5 "$f"
```

- 正常：`[ti:晴天]` `[ar:周杰伦]` 中文可读（TTPlayer 会按自己设置转成 GBK 或 UTF-8 保存）
- 乱码成 `楛㩤〤〰` 之类：交付编码又错了 → 检查 `cb[4]` 是否仍传 UTF-16LE + 字符数

反推脚本（曾用于定位）：

```bash
node -e "
```

### 9.1 IAT 修补踩坑（如果将来还要改 PE，务必先读）

- 重建导入表时**必须保留原有每个 DLL 的 `OriginalFirstThunk` / `FirstThunk` / `Name` 的 RVA 不动**，只在尾部追加新条目。把 IAT 搬到新节会导致原版代码里 `call [IAT_绝对地址]`（已由 .reloc 固化）指向未填充的内存 → DllMain 调用导入函数即崩（错误 1114）。

## 十四、桌宠联动（2026-10-29 追加）

本插件（千千静听歌词插件）**同时承担鲸鱼娘桌宠的启动钩子**，让桌宠真正"随千千静听开箱即用"。

### 14.1 架构

```
千千静听启动
  └─> 加载 AddIn\ttp_lrcsh.dll（本插件，宿主必定加载）
       └─> ttpGetSoundAddIn()   ← 钩子点：宿主主动调用，已脱离加载器锁
            ├─ 读 AddIn\whale.ini 的 [pet] follow_tt（尊重用户在托盘里关掉的开关）
            ├─ 扫进程表看 NTTWhale.exe 是否已在跑（防重复拉起）
            └─ CreateProcessA("D:\TTPlayer\AddIn\NTTWhale.exe")
```

### 14.2 为什么钩子不放在 DllMain

千千静听会**反复 load/unload** 本插件（实测单日 32 次"已加载"记录）。
DLL 被卸载时其代码段一并消失 → DllMain 派生的线程会被**静默杀掉**，
现象是"插件明明加载了、桌宠却没起来"，且**日志里一行都没有**。

因此钩点必须在**宿主主动调用的导出函数**里：调用返回前子进程已创建完毕，
此后 DLL 即便被卸载也不影响已拉起的桌宠。

> 反面教材（已踩）：第一版把 `CreateThread` 挂在 DllMain 里，睡 1.2 秒后再拉进程 ——
> 插件被卸载的瞬间线程连日志都来不及写就死了。

### 14.3 源码位置

| 内容 | 位置 |
|---|---|
| 联动实现 | `ttp_lrcsh_new.c` 的「桌宠联动」段（`pet_ensure_running` / `pet_process_exists` / `pet_follow_enabled`） |
| 钩子调用 | `ttp_lrcsh_new.c` 的 `ttpGetSoundAddIn()` 首行 |
| 桌宠本体 | `AddIn\NTTWhale.exe`（v12，17 状态 61 帧，托盘常驻） |
| 桌宠配置 | `AddIn\whale.ini` — `[pet] pos` / `topmost` / `follow_tt` |
| 反向联动 | 桌宠自己 2 秒轮询 `TTPlayer.exe`：千千静听退出 → 本体隐藏、托盘常驻；启动 → 唤醒显示 |

叠加 `eng_release()` 的 `WaitForSingleObject(3s)` 与同步 `CreateProcessA(NTTWhale.exe)`：
后者由火绒对**新编译未签名 exe** 做落地扫描时，能在 UI 线程上卡住数百毫秒到数秒——
这就是「转圈」的直接来源。

复现脚本留档在 `.workbuddy\perf\`（`mutexbench.c` 速度对比 / `pinbench2.c` PIN 压测 / `uiprobe.c` UI 往返探针，
均为 32 位，用 MinGW32 编：`gcc -m32 -O2 -o x.dat uiprobe.c -luser32 && mv x.dat uiprobe.exe`）。

### 15.2 四处改动（`ttp_lrcsh_new.c`）

| # | 改动 | 位置 | 效果 |
|---|---|---|---|
| 1 | 桌宠存活检测：`CreateToolhelp32Snapshot` 全枚举 → `OpenMutexA(SYNCHRONIZE, FALSE, "NTTWhalePet")` | `pet_process_exists()` | 17727 µs → **3.4 µs**（5172×）；删掉 `#include <tlhelp32.h>` |
| 2 | 拉起桌宠：同步 `CreateProcessA` → `cmd.exe /c start` 异步 | `pet_ensure_running()` | UI 线程不再等进程创建/杀软扫描；`cmd.exe` 是系统签名文件，已被安全软件缓存信任 |
| 3 | 拉起去抖 180 秒 | `pet_ensure_running()` 静态 `lastTick` + `InterlockedCompareExchange` | 插件一天被加载几十次也只拉起一次，不再反复创建进程 |
| 4 | `eng_release()` 只发信号不等待；工作线程自毁（关句柄、释放 `cbIface`、删关键区、`free(e)`） | `eng_release()` / `engine_worker` 尾部 | 去掉 3 秒阻塞；卸载不再等线程收尾 |

附带：`ttpGetSoundAddIn()` 首行加模块 PIN，防插件被卸载后再进回调导致崩溃。

```c
static int pinned;
if (!pinned) {
    HMODULE self = NULL;
    if (GetModuleHandleExW(GET_MODULE_HANDLE_EX_FLAG_PIN |
                           GET_MODULE_HANDLE_EX_FLAG_FROM_ADDRESS,
                           (LPCWSTR)&ttpGetSoundAddIn, &self) && self)
        pinned = 1;
}
```

> **代价**：PIN 之后 DLL 在本进程内不会再被卸载（这正是我们想要的——TTPlayer 反复枚举/卸载插件
> 才是卡顿源头之一）。若将来要热替换 DLL，必须重启 TTPlayer。

### 15.3 宠物侧改动（`whale.c` v13）

- 跟随检测轮询 `SetTimer(h, 2, 2000)` → **15000**（15 秒）。
- `WM_TIMER` 的 `w == 2` 分支首行加 `if (!g_followTT) return 0;`：关闭跟随时**完全跳过**轮询。
- 注意 `whale.c` 里的 `ttplayer_running()` **仍然是** `CreateToolhelp32Snapshot` 全枚举
  （宠物侧不改，因为 15 秒才跑一次，单次 17.7ms ÷ 15s ≈ 0.12% 单核，实测整只宠物只吃
  **0.10% 单核**）。若将来想把宠物也降到零开销，同法换成读 `TTPlayer.exe` 的命名互斥体即可，
  但需要千千静听自己建互斥体——宿主不可控，故保留现状。

跟随是「有没有在跑」的粗粒度检测，15 秒延迟对用户无感，但开销降到 1/7.5。

> **反向联动的隐藏风险（已知，未触发）**：宠物靠全进程快照找 `TTPlayer.exe`，
> 而插件用命名互斥体找宠物。两者机制不对称——若哪天把宠物换成互斥体检测，
> 记得宿主侧没有对应的对外互斥体，别把双向都改成互斥体。

### 15.5 验证

**(a) 二进制层面**（最硬的证据，不依赖日志）：

```
v3   backup: CreateToolhelp32Snapshot / Process32FirstW / Process32NextW
v3.1 现役  : OpenMutexA          ← 三个 tlhelp32 导入全部消失
```

**(b) 模块 PIN（新增行为，10 次加载/卸载压测）**：

```
pb2.exe <dll> 10   →  rc=0  elapsed=2s  DllMainHits=1
```

即**同一进程内 10 次 `LoadLibrary` + `FreeLibrary`，DllMain 只进 1 次**——PIN 生效，
宿主反复 FreeLibrary 不再真正卸载（这正是卡顿源头之一）。若未 PIN，这里会是 10。
压测脚本：`.workbuddy\perf\pinbench2.c`。

> 写这个压测踩过一个坑：自定义 `Release` 不能取 `*(PFN_REL*)pv`（那是对象首字段而非 vtable），
> 必须先 `void **vt = *(void ***)pv;` 再取 `vt[2]`，否则第一次 Release 就 SIGSEGV。

**(c) 真实宿主链路**（v3.1 上线后实测，`AddIn\log\2026-10-30.txt`）：

- **PIN 的直接后果**：`DllMain` 每进程只进一次 → 日志里每启动一次千千静听只有 **1 行**「已加载」。
  12:47:28 启动、持续观察到 13:20（**33 分钟**）仍只这一行；而 v3 时期宿主一天会产生 30–47 行
  （对照：同一个日志 00:02–00:17 的 v3 时代，每 1–16 分钟就刷一行「已加载」）。
  （注意：11:58–12:13 那几行是我自己跑 `pb2.exe` 压测产生的——每次 pb2 是**新进程**，
  所以各留一行，不是宿主反复加载。）
- 桌宠联动走新路径：日志里只有 **02:36:16 一条**「已发出拉起指令(cmd start)」——那是首次拉起。
  之后 11:13 起的宠物进程一直在跑（PID 39596），12:47 这次启动命中的是「`OpenMutexA` 已存在 →
  直接 return 不看日志」的常态短路，**既没有 `CreateProcess` 也没有刷日志**，与设计一致
  （`pet_process_exists()` 为常态路径刻意不打日志）。
- 搜索质量未退化：`周杰伦 - 晴天` QQ 0 条 / 酷狗 16 条 / 网易 8 条 → 排名 #1 892 分 →
  下载成功 2615 字节（与 v3 结果同）；`示例歌手 - 你还记得我吗` 下载 1199 字节；
  `示例歌手 - 丝路` 主选下载失败后同歌手回退命中 #2 → 下载 2068 字节（回退链路仍活着）。
- **UI 线程响应性直测**（新写的 `uiprobe.exe`：对主窗发 `WM_NULL`，用
  `SendMessageTimeout(SMTO_ABORTIFHUNG)` 量往返，QPC 计时）：
