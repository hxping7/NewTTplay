## 2. 已实证的关键事实(计划的硬地基)

1. **SAC 铁律**(本机 Win11 Smart App Control 强制,不可关闭):
   - 全新编译的未签名 EXE/DLL → **放行**(首次加载可能短暂 4551 异步裁定,重试即过);
   - 改动过**带签名**的 DLL(哪怕剥签名/改一字节)→ **永久拦截**;
   - UPX 加壳无签名 → 按恶意信誉拦截。
   → 推论:全部代码自己新写、新编译、**不加壳、不修补任何原版文件**。
2. **原版未加壳 DLL 可被我们进程加载**(`ttp_ogg.dll`/`ttp_lrcsh.dll` 均实测 LoadLibrary 成功)
   → 推论:x86 新播放器可以**进程内直接复用原版解码器**(APE/MPC/TAK/VQF/Real 等独有格式免开发)。
3. **皮肤 .skn = ZIP**,内含:每个控件一张标准 BMP + 声明式 XML(`Skin.xml` 定义全部窗口/控件/坐标/透明色
   `#ff00ff`/平铺缩放 `resize_rect`+`resize_tile`)。
   → 推论:皮肤引擎 = XML 解析 + 贴图 + 抠色异形窗口,**无格式黑盒**。
4. **播放列表(.ttbl)与曲库(Music.library)是同一 `TTBL` v5 容器**,字符串 UTF-16LE,内含 hash 类字段待解。
5. **配置 TTPlayer.xml / 每皮肤伴生 .xml 均为明文 XML**(窗口布局、字体、配色已可读)。
6. TTPlayer 全家(x86)在本机可正常运行 → 任何"1:1"行为疑问都可**双开对照**实测。

## 4. 架构决策(ADR)

**ADR-1 技术栈:C + Win32/GDI,MinGW i686,x86 单进程单 EXE**
- 为什么 x86:才能进程内加载原版 x86 解码器 DLL(事实 #2);
- 为什么纯 Win32:1:1 的本质是 GDI 时代的像素级贴图 + 分层窗口 + 抠色异形窗,
  Web 框架(Electron/WebView2)在异形窗、点击穿透桌面歌词上全是逆水行舟;
- 为什么不用 .NET/Qt:需新装工具链;自包含包体大;Qt 的皮肤化照样要手写;MinGW32 已验证可过 SAC;
- 已否决:Node+WebView2(SAC 最稳但解码桥/异形窗都要自造,复杂度转移而非消除)、修补原版 exe(SAC 铁律 #2)。

**ADR-2 解码策略:双轨制**
- 轨 A(内置,公有领域单文件库):MP3(minimp3)、WAV、OGG(stb_vorbis)、FLAC(dr_flac)——覆盖 90% 曲库,零法律风险;
- 轨 B(进程内加载原版 DLL):APE/MPC/TAK/VQF/Real/AC3-DTS/mp3PRO——ABI 待逆向(W2),同工厂模式,高把握;
- 原版 DLL 只在本机引用,**绝不随产品分发**;轨 B 失败不影响轨 A 完整可用。

**ADR-3 数据策略:独立目录 + 单向导入**
- 新程序住 `D:\NTTPlayer\`(src/docs/deps/),数据自有副本;导入器只读 `D:\TTPlayer`;
- 配置 schema 兼容读原版 TTPlayer.xml,写自己的 `NTTPlayer.xml`(字段名尽量同名);
- 原版随时可开,作为 1:1 对照的"金标准"。

**ADR-4 歌词子系统:代码并入,消灭 DLL 形态**
- `ttp_lrcsh_new.c` 的音源/HTTP/JSON 模块抽出复用;同时保留其独立 DLL 形态给原版 TTPlayer 用(两不误)。

**ADR-5 AI:本地配置、协议兼容、可全关**
- 设置面板配 LLM API 端点(OpenAI 兼容协议,支持任意厂商/本地模型);
- 所有 AI 功能默认关;关掉后是纯血 1:1 克隆。

## 8. 合规边界(一句话版)

逆向的是**格式、协议、行为**(合法互操作范畴),反编译的**代码一行不进仓库**;
原版二进制(解码器/皮肤)只在本机引用、绝不分发;「新天天静听」名称仅个人使用,公开发布前须改名。
AI 生成内容(翻唱/改编)仅限个人使用——涉及原曲著作权与声音肖像,生成物不得对外分发。
